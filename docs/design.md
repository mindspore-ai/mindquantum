# 实现原理

[首页](../README.md) · [使用指南](usage.md) · [基准与性能](benchmarks.md) · 实现原理

DSB 和 BSB 反复执行同一种更新：先计算变量之间的耦合，再更新每个变量的位置与动量。
耦合需要组合不同变量的信息，后续更新则可以逐元素完成。这一区别决定了 NPU 上的计算分工。

## 一步迭代计算什么

对一个副本，记第 t 步的位置为 $x_t$、动量为 $y_t$，压力值为 $p_t$。
DSB 用位置的符号计算耦合，BSB 直接使用位置：

$$
u_t=\begin{cases}
\operatorname{sign}(x_t), & \text{DSB},\\
x_t, & \text{BSB}.
\end{cases}
$$

得到耦合项 $Ju_t$ 后，先更新动量，再用新动量更新位置：

$$
v=y_t+dt\big[(p_t-\delta)x_t+\xi(Ju_t+h)\big],
\qquad z=x_t+dt\,\delta v.
$$

最后逐元素处理边界：若 $|z_i|>1$，将位置截到 $\operatorname{sign}(z_i)$，动量清零；
否则保留位置 $z_i$ 和动量 $v_i$。边界判断是严格大于，位置恰好为 ±1 时保留动量。
迭代内部使用 `sign(0)=0`；最终评分时把零位置归为自旋 +1，是另一个步骤。

接口中的 `delta`、`xi`、`dt` 分别对应 $\delta$、$\xi$、$dt$，默认值见 [Solver 参数](usage.md#solver-参数)。
两种算法的差别只在 $u_t$，因此可以共用动量更新、位置更新和边界处理。

## 把一批搜索合成一次矩阵乘

对一个副本，$Ju_t$ 是矩阵与向量相乘。对共享 `J` 的一批副本，将位置按列组成矩阵 `X`，
所有耦合便成为一次矩阵乘：BSB 计算 `J @ X`，DSB 计算 `J @ sign(X)`。
原本彼此独立的搜索由此共用读入的 `J`，提高矩阵数据的复用程度。

矩阵乘交给 **Cube**，通过 CANN 的 `aclnnMatmul` 执行，由算子库选择硬件分块策略。
得到整批耦合结果后，**Vector** 在一个 AscendC 内核中完成动量、位置和边界更新。
DSB 下一步需要的符号也在这个内核中生成，避免再为它读取一次位置。

这条路径每步只保留矩阵乘与融合更新两个主要计算阶段。中间的逐元素运算不需要各自启动内核，
实现也只需维护算法特有的状态更新，而把通用矩阵乘留给 CANN。

精度选择发生在矩阵乘处：FP32 使用 `cubeMathType=0 (KEEP_DTYPE)`，HF32 使用 `3 (USE_HF32)`。
两种模式的状态存储和 Vector 更新均为 FP32，执行期间不会自动切换精度。

## 把固定的迭代留在设备上

矩阵乘和融合更新确定了单步计算，但一次求解要重复执行许多步。
只要问题、形状和压力序列固定，每步需要提交的任务及其依赖也就固定；变化的是初态和迭代中的数据。

因此，构造 Solver 时就校验并保存 J/h/p 快照，分配设备缓冲区、算子工作区和页锁定主机缓冲，
预热算子，再把完整迭代捕获为**执行图**。每次 `run` 写入新的初态，重放这张图，最后取回结果。

```diagram
┌──────────────────────────────────────────┐
│ Construct: J / h / p → buffers + graph   │
└────────────────────┬─────────────────────┘
                     │ reuse
                     ▼
┌──────────────────────────────────────────┐
│ run(x0, y0)                              │
│ upload → [Cube → Vector] × n_iter        │
│        → download → return x, y          │
└──────────────────────────────────────────┘
```

主机通过一次 `aclmdlRIExecuteAsync` 提交整张图，迭代之间没有主机同步或状态往返。
DSB 的首轮符号初始化也在图内；BSB 直接使用位置。最终结果下载完成后，`run` 才返回。
将准备与执行分开，正是重复调用可以摊销构造成本的原因。

执行图会继续引用张量和缓冲区，因此这些资源的生命周期必须与执行计划一致。
每个 Solver 独立持有 context、stream、算子执行器、张量和内存。关闭时先结束设备工作并销毁图与执行器，
再释放张量和内存，最后销毁 stream 与 context。同一对象的调用通过互斥锁串行执行；
原生层先释放 Python GIL 再等待锁，避免锁与 GIL 的等待关系造成死锁。

## 让数据布局配合这条计算路径

Python 接口用 `(N, batch)` 表示状态，一列对应一个副本。设备端将按列连续的数据视作
`(batch, padded_n)`，使一个副本仍占据连续内存，同时用转置视图完成矩阵乘：

$$
(JX)^T=X^TJ^T.
$$

这里保留了右侧的转置，不依赖 `J` 对称。非对称矩阵测试用于检查布局变换没有改变数学含义。

`padded_n` 将 N 补齐到 64 的倍数，补入行列为零。64 个 FP32 元素正好是 256 字节，
满足 910B `CompareScalar` 比较指令的分组要求，也满足数据搬运与矩阵乘的对齐要求。
补齐只存在于内部，返回 Python 的仍是原始变量数。

Vector 的划分单位是整批状态中的元素，而不是完整副本。这样，即使副本数不能被核数整除，
也能按元素数均衡负载。外场 h 在构造时按 batch 展开一次，让跨副本的更新块能够连续读取外场。

每个 Vector 核按最多 4096 个元素分块，显式使用约 112.5 KiB 的 UB（片内工作内存），另为 CANN 临时区保留 8 KiB。
片内缓冲区随块大小确定，不随问题规模增长；设备上的稠密 `J` 仍占用 $O(N^2)$ 内存。
执行图也会随迭代步数增长，超长序列可能触及 CANN 运行时资源限制，此时直接报错。

## 修改后怎样确认计算仍然正确

以上职责分别由下面的模块持有。数据转换与评分留在 CPU 侧，不进入设备迭代；
QPLIB 的[系数约定与独立评分](benchmarks.md#qplib-文件中的系数约定)决定了基准结果应如何解释。

| 位置 | 负责什么 |
| --- | --- |
| [`kernel_sb.py`](../kernel_sb.py) | 公共 API、输入校验、快照与形状处理 |
| [`host/kernel_sb_wrapper.cpp`](../host/kernel_sb_wrapper.cpp) | 原生执行计划、设备资源与执行图 |
| [`kernel/kernel_sb_kernel.cpp`](../kernel/kernel_sb_kernel.cpp) | 融合状态更新内核 |
| [`qplib.py`](../qplib.py) | 下载、解析、Ising 转换与原始目标评分 |
| [`benchmarking.py`](../benchmarking.py) | 同初态 CPU 参考、计时与结果记录 |

短轨迹以独立 FP64 方程的计算结果为参照，核对最终位置与动量，覆盖非对称 J、严格边界、补齐尾部和跨块掩码。
这类测试回答的是更新方程是否正确，资源测试则检查快照、重复执行、关闭和并发调用是否符合约定。

比较不同计算路径的长轨迹时，浮点归约顺序的微小变化可能被非线性迭代放大，不能要求结果逐元素完全相同。
此时检查最终可行性与原始目标值分布，再比较性能。先验证方程、再验证搜索质量，才能判断一次提速是否保留了求解能力。
具体命令见[验证与排错](usage.md#验证与排错)，性能测量见[基准与性能](benchmarks.md)。
